# Live Encode API (MVP)

Entrypoint: `python/api/app.py`

Run:

```bash
uvicorn python.api.app:app --host 0.0.0.0 --port 8000
```

## Endpoints

- `POST /encode`
- `POST /decode_frame`
- `POST /encode/{stream_id}/play`
- `POST /encode/{stream_id}/pause`
- `POST /encode/{stream_id}/resume`
- `POST /encode/{stream_id}/seek`
- `POST /encode/{stream_id}/heartbeat`
- `GET /encode/{stream_id}/player`
- `GET /encode/{stream_id}/playlist.m3u8`
- `GET /encode/{stream_id}/segments/{seq}.ts`
- `GET /encode/{stream_id}/status`
- `POST /action/invalidate`

## Notes

- `python/api/app.py` is a thin FastAPI entrypoint that wires encode and decode route modules.
- The browser player logic now lives in `python/api/lib/player_page.js`, while `python/api/lib/encode_runtime.py` only renders the HTML shell and injects runtime config.
- MVP supports `http(s)` MP4 source URLs only.
- `ffmpeg` and `ffprobe` must both be available in `PATH`.
- Source metadata is fetched with a remote-first `ffprobe` pass and falls back to a short local probe copy when needed.
- If remote metadata probing falls back to a local probe copy, that validated local file is reused as the session spool seed.
- Source media is progressively spooled into a temp MP4 file.
- Initial source warmup may take up to 30 seconds while the backend stabilizes the source connection and fills startup buffer.
- Transient source-open failures are retried automatically inside the backend before they are exposed as a final error.
- First play waits for a locally readable spool file, not just a rough downloaded-byte threshold.
- HLS output is generated by a session-local ffmpeg writer in a temp directory.
- The playlist and segments are served from temp files, not rebuilt in Python memory.
- No TTL or background GC is included in this iteration.

## `POST /encode` Settings

- `device`: `CPU` or `CUDA_0`
- `model_type`: `P`, `Q`, `C`, or `B`
- `inference_scale`: `1.0`, `0.75`, or `0.5` (default `0.5`)
- `prebuffer_seconds`: default `4`
- `segment_seconds`: default `2`
- `gpu_batch_target`: default `60`
- `gpu_batch_max`: default `64`
- `gpu_flush_ms`: default `12`
- `use_nvenc`: default `true`

## `POST /decode_frame` Settings

- `file`: required multipart local image upload
- `device`: `CPU` or `CUDA_0` (default `CPU`)
- `model_type`: `P`, `Q`, `C`, or `B` (default `P`)
- Success response returns decoded `wm_secret` as an integer
- Invalid or empty image uploads return `400`
- Valid images with no detectable watermark return `422`

## Simplified Playback Control

- `POST /encode/{stream_id}/play` is the authoritative start or restart primitive.
- `POST /encode/{stream_id}/pause` is the authoritative stop-and-remember primitive.
- `POST /encode/{stream_id}/resume` is a compatibility wrapper that calls `play(saved_position_seconds)`.
- `POST /encode/{stream_id}/seek` is a compatibility wrapper that calls `play(targetPosition)`.
- `POST /encode/{stream_id}/heartbeat` only updates `position_seconds` and client liveness.
- Far seek is implemented as `play(targetPosition)` with a short rebuffer.
- Audio and video restart from the same anchor because the ffmpeg HLS writer seeks the audio input with the same `anchor_time_seconds`.

## Invalidation Action

- `POST /action/invalidate` accepts `wm_secret`.
- All matching encode sessions are force-stopped and moved into terminal `invalidated` state.
- Invalidated sessions cannot be played, paused, resumed, sought, or heartbeated again.
- The player page shows `The current session has been invalidated.` and disables all controls.

## Heartbeat And Timeout

- The player sends heartbeat updates every 10 seconds while buffering or streaming.
- If no heartbeat arrives for 30 seconds, the backend auto-pauses the active generation.
- Status polling is informational only and no longer acts as a keepalive.
- Browser close handling may send a best-effort pause request, but correctness depends on the 30-second heartbeat timeout.
- During explicit play, the frontend remains in loading state until both source warmup and HLS prebuffer are ready.
- The visible player timeline stays pinned during buffering and only starts advancing once local playback actually begins.
- The extracted player frontend uses a single injected config object and the simplified `play/pause/heartbeat` control model.

## `inference_scale` Behavior

- Frames are downscaled before watermark inference when `inference_scale < 1.0`.
- Watermark inference runs on the scaled frames.
- Encoded frames are upscaled back to the original source resolution before entering the continuous ffmpeg HLS writer.
- This mirrors the working Gradio live encode behavior; it is not watermark-strength control.

## Recommended Flow

1. `POST /encode`
2. Open returned `player_url` in a browser
3. Press `Play` to start the backend warmup and buffering cycle
4. Pause, resume, and far seek are handled on the same player page without reload

## Debugging

- Watch the API server console logs while using `player_url`.
- The backend logs metadata probing, spool progress, generation start and stop, ffmpeg HLS writer startup, and worker failures.
- `GET /encode/{stream_id}/status` exposes `saved_position_seconds`, `logical_position_seconds`, `anchor_time_seconds`, `last_client_position_seconds`, `last_heartbeat_at`, invalidation metadata, and spool warmup diagnostics including retry state.
- Temp spool files and temp HLS directories are cleaned up when the server process exits.
